# 두 시그널에서 한 비트씩 확인하는 프로토콜까지

처음 서버에 들어온 것은 `SIGUSR1`과 `SIGUSR2`를 0과 1로 해석해 여덟 번 밀어
한 바이트를 만드는 코드였다. 첫 클라이언트는 비트를 보낸 뒤 150µs를 쉬었다.
`f8414c4` 커밋의 `send_bit`은 다음과 같았다.

```c
if (kill(server_pid, signal) == -1)
	return (-1);
usleep(150);
```

이 간격은 느린 환경에서 서버가 처리할 시간을 늘릴 뿐, 처리 완료를 확인하지
않는다. 표준 시그널은 같은 종류가 처리 전에 여러 번 오면 발생 횟수를 모두
보존하는 큐가 아니므로 장문이나 부하가 달라지면 비트가 사라질 수 있다. 시간을
조정해서 우연히 통과시키는 대신, 서버가 한 비트를 소비했다는 응답을 받은 뒤
다음 비트를 보내도록 `3407483`에서 stop-and-wait 흐름을 붙였다.

## 바이트 경계와 메시지 경계는 별개다

클라이언트는 최상위 비트부터 보낸다. 현재 `src/client.c`의 `send_byte`도 같은
비트 순서를 유지한다.

```c
shift = 7;
while (shift >= 0)
{
	status = send_bit(server_pid, (byte >> shift) & 1, *sequence,
			server_path);
	if (status != 0)
		return (status);
	(*sequence)++;
	shift--;
}
```

서버는 매 비트마다 기존 값을 왼쪽으로 밀고 1 시그널일 때 마지막 자리를 세운다.
여덟 비트가 모여야 한 바이트를 외부로 내보낸다.

```c
g_current_byte <<= 1;
if (event->signal == MT_ONE_SIGNAL)
	g_current_byte |= 1;
g_received_bits++;
if (g_received_bits == 8)
{
	output = g_current_byte;
	if (flush_byte(output) == -1)
		return (-1);
	g_current_byte = 0;
	g_received_bits = 0;
}
```

여덟 비트만으로는 문자열이 끝났는지 알 수 없다. `f813369`에서 본문 뒤에 NUL
바이트를 하나 더 보내고, 서버는 이를 출력하는 대신 줄바꿈과 세션 종료로
해석하도록 정했다. 그래서 빈 문자열도 아무것도 보내지 않는 호출이 아니라 NUL
프레임 하나다. 반대로 본문 중간의 NUL을 보존하는 바이너리 프로토콜은 아니다.

## ACK 시그널도 출처와 순서를 말해 주지 못했다

초기 ACK는 별도의 시그널 하나였다. `sigsuspend`로 기다리는 방식은 고정 지연보다
낫지만 응답 안에 “어느 서버가 몇 번째 비트를 확인했는가”가 없다. 늦게 도착한
응답, 다른 프로세스가 보낸 같은 시그널, 두 클라이언트가 섞이는 경우를 구분할 수
없었다.

뒤이은 세션 프로토콜에서는 응답을 Unix datagram 구조체로 옮겼다. 비트 데이터는 여전히
`kill`로 보내지만 예약에는 nonce, 비트 ACK에는 증가하는 `sequence`를 넣는다.
클라이언트는 응답 경로, magic, 서버 PID, 종류와 token이 전부 맞는 패킷만
받는다. 시그널 두 개라는 연습 범위를 유지하면서도 확인 응답에 필요한 정보는
별도 채널로 보낸 선택이다.

PID 문자열도 단순 `atoi`로 읽지 않는다.
[`src/parse_pid.c`](../src/parse_pid.c)의 `mt_parse_pid`는
숫자를 더하기 전에 `INT_MAX` 범위를 확인하고, 0과 1을 서버 PID로 거절한 뒤
`pid_t` 왕복이 같은지 본다. 그 다음 `kill(pid, 0)`은 해당 번호의 프로세스가
보이는지만 확인한다. 확인 직후 PID가 재사용될 수 있고 같은 UID 프로세스를
인증하지도 않으므로, 이것을 신원 보장으로 확대하면 안 된다.

초기 프로토콜의 문제를 고친 순서는 NUL 종료, 비트별 ACK, 대기 시간 상한, 세션
소유권, 출처와 순번이 있는 응답 채널, self-pipe 순이었다. 뒤의 네 기록은 이
가운데 대기, 시그널 처리 문맥, 세션 회수와 프로세스 검증을 각각 더 깊게 다룬다.
