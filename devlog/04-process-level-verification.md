# 프로세스 수준 장애 검증

## 함수 호출만으로는 프로토콜을 검증할 수 없다

시그널 전달, PID 수명, 상속 마스크, Unix 소켓 경로와 stdout pipe는 실제
프로세스 경계에서 상호작용한다. Makefile의 `test`는 제품 두 실행 파일과 보조
프로그램을 만든 뒤 다섯 셸 검사를 순서대로 실행한다.

| 검사 | 실제 경계 |
| --- | --- |
| `tests/smoke.sh` | 빈 문자열, UTF-8, 1,024바이트 메시지, 잘못된 PID |
| `tests/session_ownership.sh` | 죽은 소유자 회수, 살아 있는 소유자의 BUSY |
| `tests/response_validation.sh` | 잘못된 응답 뒤 올바른 READY·ACK 선택 |
| `tests/output_failure.sh` | stdout 부분 쓰기·`EINTR`·0·`EPIPE` |
| `tests/protocol_regressions.sh` | 경로 권한, 오래된 파일, timeout, STOP/CONT, 포화 |

검사는 다음 경쟁 조건을 의도적으로 만든다.

- 메시지 도중 클라이언트 종료 뒤 새 예약
- 살아 있는 소유자와 두 번째 클라이언트의 경쟁
- 서버 또는 클라이언트의 STOP/CONT
- 잘못된 출처·크기·magic·PID·token 응답의 연속 유입
- 데이터 시그널을 막은 상태로 실행한 클라이언트
- 같은 소켓 경로에 남은 소켓과 일반 파일

차단 마스크 검사는 `tests/masked_exec.c`로 만든 보조 실행 파일을 통해
클라이언트를 실행한다. 클라이언트는 ACK를 시그널이 아니라 Unix datagram으로
받기 때문에 이 상태에서도 동작한다. 서버의 상속 마스크까지 확인하는 사례는
아니다.

## 시간 검사는 상한과 원인을 함께 본다

시간 초과 검사는 너무 짧게 끝났는지만 보지 않고, 잘못된 응답이 이어져도
`client: timed out waiting for acknowledgement`로 끝나는지 확인한다.
`protocol_regressions.sh`의 허용 범위는 2~6초다. 공유 머신의 스케줄링 오차는
허용하지만 상대 timeout을 패킷마다 초기화하는 구현이 계속 대기할 만큼 넓히지
않는다.

## 장애 주입은 출력 확정 지점을 겨냥한다

테스트 서버는 `write`를 치환해 본문과 줄바꿈 각각에서 짧은 쓰기, `EINTR`, 0, `EPIPE`를 만든다. 핵심 조건은 단순한 프로세스 종료가 아니라 실패한 바이트의 ACK가 나가지 않는지다.

프로토콜 검사는 정상 결과, 잘못된 응답의 무시, 시간 제한, 종료 상태와 정리된
파일 경로를 함께 확인한다. 각 스크립트는 `trap`에서 남은 프로세스와 임시
디렉터리를 정리하고, 정상 종료 경로에서는 클라이언트·서버 소켓이 사라졌는지도
본다. 출력만 맞추면 남은 프로세스나 오래된 socket이 다음 사례를 오염시킬 수 있다.

```sh
make test
```

셸 기반 시간 검사는 운영체제 스케줄러와 시스템 부하의 영향을 받는다. 또한 같은
UID 공격자에 대한 자격 증명, 서버가 데이터 시그널을 차단한 채 시작하는 경우와
장시간 부하는 별도 검증이 필요하다.
